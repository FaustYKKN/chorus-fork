## 决策定稿（2026-07-22 评审）
用户拍板，作为本 SPEC 的硬约束：
- **模型 B**：团队是**公司内的子组**（不是独立公司）。公司仍是租户边界。
- **项目归属 0 或 1 个团队**（严格单团队，不跨团队共享）。
  - 归某团队的项目 → **仅该团队成员可见**。
  - 不归任何团队的项目（`groupUuid = null`）→ **公司级，全员可见**（存量项目默认落这）。
- **成员多对多**：一个人可加入多个团队。
- **人人可建团队**，创建者即**组长**；组长在成员页**勾选公司内用户**加人。
- 不引入"公司管理员"角色——团队由各自组长自管；平台仍只有超管（跨公司）。
- **迁移**：走方案 **(b)**——现有 ProjectGroup 转团队，owner=公司管理员、成员=当前全体用户。
- **生命周期**：团队**本期不可解散/删除**；普通成员**可自行退出**；**创建者（组长）不可退出、不可被移除**；本期**不支持易主**。

## 1. 为什么要做
现状：公司是唯一隔离边界，**同公司内所有人看到所有项目/任务**（查询只按 `companyUuid` 过滤，无用户-项目成员关系）。40 人规模下需要"小组各管各的看板、各自的人"，且要自助、去中心（组长自管），而不是全塞给超管。

## 2. 现状盘点
- `ProjectGroup`(companyUuid, name, description)：已是"公司内项目分组"，但**无 owner、无成员**。
- `Project.groupUuid`(可空 → ProjectGroup)：**"项目属于哪个组"已建好**。
- `Task/Idea/Document/Proposal/Activity` 挂在 Project 下，天然继承项目的团队归属。
- 无 `Team / Member / Role` 表；`User` 无角色字段。
- 项目/任务/仪表盘计数等**几乎所有列表查询只按 `companyUuid`**（见 §7 影响面）。

## 3. 数据模型（复用 ProjectGroup，最少新增）
- `ProjectGroup` 新增 **`ownerUuid`**（创建者=组长，指向 User.uuid）。
- 新增 **`TeamMember`**：`{ id, uuid, groupUuid, userUuid, role: "owner"|"member", createdAt }`，`@@unique([groupUuid, userUuid])`，按 `groupUuid`、`userUuid` 建索引。
  - 一个用户在多个团队 = 多行；`role=owner` 与 `ProjectGroup.ownerUuid` 对应（owner 恒为成员）。
- `Project.groupUuid` 语义升级为**访问控制边界**（原来只是 UI 分组）。
- UI 文案统一叫"团队"（ProjectGroup 仍是内部实体名）。

## 4. 可见性规则（核心，可执法）
对公司 C 内的普通用户 U：
- **R1**：U 看得到某**团队**，当且仅当 U 是其成员（owner 或 member）。"我的团队"列表 = U 的成员团队。
- **R2**：U 看得到某**项目**，当且仅当：项目 `groupUuid = null`（公司级/全员）**或** 项目所属团队是 U 的成员团队。
- **R3**：`Task/Idea/Document/Proposal/Activity` 的可见性**继承其所属项目**（R2）——项目不可见则其下全部不可见。
- **R4**：任何公司用户可**创建团队** → 自动成为该团队 `owner` + 写一条 `TeamMember(owner)`。
- **R5**：仅**组长**能管理团队：加/删成员、改名/简介、把项目归入/移出本团队。**本期不提供解散/删除团队**。
- **R5.1**：普通成员**可自行退出**团队（删自己的 TeamMember 行）；**组长不可退出、不可被移除**（本期无易主）。
- **R6**：仅团队**成员**能在该团队下**新建项目 / 看到其看板**。把已有项目归入某团队要求操作者是**该团队成员**（组长优先）。
- **R7**：team-less（公司级）项目沿用现状——任何公司用户可见、可建（不回退现有能力）。
- **R8**：严格单团队——项目至多属于一个团队；**无跨团队共享**。跨团队协作走"派给人"（后续，参照 agent 归属），本期非目标。
- **R9**：Agent/MCP 可见性——Agent 代表其 owner 行事，**Agent 的可见范围 = 其 owner 的成员团队 + 公司级项目**（见 §8 开放问题，需确认）。
- **R10**：既有 **agent 归属隔离不变**（只能派给自己的机器）；团队成员关系**不**赋予驱动他人机器的权力。
- **R11**：超管（平台）不受影响——无 companyUuid 上下文，只管公司+用户。

## 5. 成员与自助建团队
- **建团队**：`POST /api/teams`（或复用 project-group create）——company 用户 → 建 ProjectGroup（ownerUuid=actor）+ TeamMember(owner)。
- **加成员**：组长在成员页从**本公司用户列表**勾选加入（写 TeamMember(member)）；可移除（删行，owner 不可被移除）。
- **多团队**：join 表天然支持；用户在各团队里角色独立。
- **组长专属页**：成员增删、改名、该团队项目管理、解散。普通成员只读成员 + 用团队看板。

## 6. 存量迁移（**需你确认，见 §9-Q1**）
现有带 `groupUuid` 的项目若直接生效 R2，会**对非成员瞬间隐藏**。两个安全选项：
- **(a) 存量项目一律置 team-less**（`groupUuid=null`）：所有人可见度不变，团队从零起步（丢失原分组信息）。
- **(b) 现有 ProjectGroup 转团队**：owner = 公司管理员（DEFAULT_USER），成员 = 当前公司**全部用户**（切换当天无人失去可见），组长后续裁剪。**推荐 (b)**（保留分组、零失访、可渐进收紧）。

## 7. 影响面（可见性重写——本功能最大、最需测的部分）
所有"列给用户看"的查询要从"按公司"改成"按 U 的成员团队 + 公司级项目"：
- `project.service`（列表/计数）、`task.service`（列表/`getTaskAttentionSummary`/仪表盘）、`idea/document/proposal/activity` service。
- dashboard、graph、项目/任务页的服务端取数。
- MCP 工具（discover/任务列举）——按 R9 用 agent owner 的团队过滤。
- 写入面校验：建项目/归组/建任务时校验 R5/R6（防越权把项目塞进非自己团队）。

## 8. 分阶段实现
- **P1 模型 + 自助建团队**：schema（ownerUuid + TeamMember）+ 迁移(§6) + 建团队/成员 CRUD API + 咽喉校验(R4/R5/R6) + 单测。**不改可见性**（此阶段全员仍可见，行为不变）。
- **P2 可见性重写**：把 §7 全部读查询接入"成员团队 + 公司级"过滤 + 端到端可见性测试（成员/非成员/组长/Agent 各视角）。**风险集中在这一阶段**。
- **P3 组长管理页 + 团队看板 UI**：我的团队、建团队、成员勾选器、项目归团队、团队维度仪表盘。

## 9. 决策记录（已拍板 2026-07-22）
- **Q1 迁移**：✅ **(b)** —— 现有 ProjectGroup 转团队，owner=公司管理员、成员=当前全体用户。
- **Q2 Agent 可见性**：✅ 确认 R9——agent 范围=其 owner 的成员团队 + 公司级项目。
- **Q3 公司级项目建权**：✅ 沿用"任何公司用户可建 team-less 项目"。
- **Q4 生命周期**：✅ 团队本期不可解散；成员可自退；组长不可退/不可移除；不支持易主。

## 10. 验收标准（端到端）
- 甲建团队 T1、拉乙入伙；丙非成员。丙在项目/任务/仪表盘/graph/MCP discover **全都看不到** T1 的项目与任务；甲乙能看到。
- team-less 项目：甲乙丙**都**看得到（现状不回退）。
- 丙尝试把某项目归入 T1（非成员）→ 拒绝(403)。
- 一人可同时在 T1、T2，两边看板都在、互不串。
- 既有 agent 归属隔离用例仍全绿；agent 列任务的范围符合 R9。

## 11. 非目标（本期不做）
- 跨团队共享同一项目 / 项目多团队。
- 公司管理员角色、跨团队汇总看板。
- 团队级邀请码（本期用"组长勾选公司用户"加人；邀请码是公司级、决定入哪个公司，与团队正交）。
