# SPEC：无人值守批量执行（睡觉跑批）

状态：**待评审**　负责人：小杨　起草：2026-07-15　fork：chorus-fork（daemon + server）

## 目标（一句话）

睡前给一个 agent 批量指派 N 个任务 → 整夜**串行自动跑、不阻塞** → 早上醒来,每个任务要么
**to_verify**(做完了、等人验收),要么被**明确标出**(失败/超时/没提交)。批次**绝不因为某一个坏任务
死停**,也**绝不静默丢任务**。

**验收画面(早上看板):** `8 待验收 · 1 超时 · 1 没提交(已自动催过)` —— 一眼看清,该验的验、该管的管。

## 统一机制(全部挂在一根已有的线上)

daemon 每次唤醒**开始报 `running`、结束报 `ended`、崩溃报 `interrupted(crash)`,都带这个任务的 uuid**
(已验证:`cli/waker.mjs` → `advanceTurn(status, entity)`)。服务端 `turn-advance` 端点**现在收了这个信号
却只存不用**。本 SPEC 基本就是:**把这根线接到"任务状态机 + 未完成检测 + 跑飞保护"上**,全程不依赖模型记性。

## 已有的韧性（查证过,不用重造）

- **daemon↔Chorus 断线重连:有。** SSE 断了按**退避自动重连**(`sse-listener.mjs` reconnectTimer/backoff);
  重连后 **backfill 补投**掉线期间的待办任务(re-drive pending turns),`seen` 集去重不重跑。
  → 睡觉时网络抖一下,批次**不丢、不重复**。(唯一例外:`connection_conflict`=同目录被别的 daemon 占了,
  故意不重连——那是双开保护,非网络抖动。)
- **opencode 子进程健康:无。** daemon **持续读 opencode 的输出流**(NDJSON,已在读),但**不判"卡死 vs 在干活"、
  也完全没有超时**——这正是 R5 要补的,也是你担心的 429/500/内存卡死的落点。
- **daemon 进程本身:** 靠 systemd/开机自启常驻;它自己挂了整批停(既有运维项,不在本 SPEC)。

## 需求

### R1 — 队列自动推进(不阻塞的核心)　【基本已有,需坐实】
- 每个被指派的任务 → 一个 wake 入队;同目录 wake 共用一条车道串行(Layer 1 WakeQueue);
  **上一个子进程退出 → 下一个自动开跑**,无论上一个成功/失败/崩溃(`wake-queue.mjs` `#pump` 链式推进 +
  "poisoned wake 不堵车道")。
- 要做:一个**批量 drain 测试**坐实"10 个任务全入队、逐个跑、坏的不堵后面的"。前提:指派要真正触发
  `task_assigned`(UI Server Action / MCP `chorus_pm_assign_task` 会;裸 REST /claim 不会)。

### R2 — `running` → `in_progress`（状态准确）　【新】
- daemon 报 `running`(任务 X)→ 服务端把 X 从 assigned 置 **in_progress**。
- 排队中(turn 未 running)的任务**留在 assigned**,如实显示"在排队"。
- **硬保障、零模型依赖**。取代现在"要 agent 自己调 report_work status=in_progress"这一步。

### R3 — `ended` 但仍 `in_progress` = 干完没提交　【新,核心】
deterministic 三层,每层必触发:
1. **检测(硬保障):** 报 `ended`(X) 时 X 还在 in_progress = agent 走了没提交 → 平台必然知道。
2. **聚焦重唤醒(高成功率):** 自动发**一条极短单一目的唤醒**——"任务 X 运行结束但没提交,现在调
   `chorus_submit_for_verify`,或用 `chorus_report_work` 说明卡在哪"。短 prompt = 没有 skill/plan/长上下文
   抢注意力(当初就是被这些挤忘的)。走已有的 re-dispatch 通道(`dispatchResume`/`deliver_turn`)。
   **上限 K 次**。
3. **兜底转人工:** K 次仍不提交 → 看板标黄"干完没提交,需人处理"。
- **诚实边界:** 做不到 100% 自动提交——"活到底做完没、对不对"要判断,自动提交没做完/失败的活比不提交更糟。
  能保障的是**"绝不静默烂掉":检测必然 + 聚焦重唤醒(比长任务里成功率高得多)+ 人工兜底**。

### R4 — 崩溃隔离 + 状态标记（interrupted）　【新】
- 队列继续已有(WakeQueue 防呆)。补:报 `interrupted(crash)`(X) 且 X 在 in_progress/assigned →
  **标 X 为 needs-attention(失败)**,批次继续下一个。
- 可选:对疑似瞬时崩溃(模型 API 抖动)**1 次有限重试**再标失败(见 R7)。
- **绝不 wedge、绝不静默。**

### R5 — 卡死/跑飞保护:空转优先 + 硬顶　【新,已验证缺失】

**先分清两种"挂"——它们要用不同信号,不能混:**

| 情况 | "进程还在吗?" | 谁来抓 |
|---|---|---|
| 进程**死了**(崩溃 / 被系统 OOM 杀 / 报错退出) | 不在了 | **操作系统的 `close` 事件——秒级、免费、不用轮询**。daemon 已收(→ R4 标失败、跑下一个)。**你担心的"内存过大被杀"就在这**:一被杀进程就没,马上知道。 |
| 进程**还活着、但卡住了**(挂在 429/500 死等) | **"还在啊"** | ← **这就是坑**:进程没死,问"还在不在"回答"在",一点用没有。只能看"它还在不在**干活**"。 |

所以"轮询进程是否存活"**解决不了卡死**——卡死的进程恰恰是活的。要抓的是"活着但不干活",得看**进度信号**。

- **现状**:daemon 已在持续读 opencode 输出流,但**对"活着但卡住"完全没有检测、没有超时**——干等到天亮。
- **两道闸**(针对"活着但卡住"):
  1. **空转超时(主,分钟级)**:opencode 输出流静默超过 **T_idle(默认 12 分钟,可配)** → 判卡死 → 杀子进程。
     **这才是治 429/500/内存卡死的正解**——它们的共性是"不再产出",几分钟就抓到,**不用死等 40 分钟**。
  2. **硬顶(兜底,40 分钟)**:无论有没有输出,单任务墙钟超 **40 分钟** → 杀。防"慢性跑飞"。
- 杀掉后 → 标 needs-attention(timed-out) → **有限重试 1 次**(429/500/OOM 常是瞬时) → 仍失败则跑下一个 + 标人。
- **调参注意**:若某任务有"长时间静默的合法操作"(如 10 分钟编译/测试,其间 opencode 无 NDJSON 输出),
  可能被空转误杀 → 调大 T_idle;**更稳的可选升级(v1.5):看子进程 CPU 活性**(卡死=CPU 静默,编译=CPU 忙),
  比"看输出"更准。

### R6 — 早上一览(可观测)　【新/增强,建议 v1.5】
- 批次/该 agent 过夜的汇总:`to_verify / failed / timed-out / didn't-submit / still-running` 计数,
  看板一个筛选或一张卡片。让"醒来知道结果"落地。

### R7 — 模型/API 错误退避　【可选,建议 v1.5】
- wake 因模型 API 限流/宕机失败 → 有限次退避重试,而非立刻判失败。避免整夜任务被瞬时抖动带走。
  可并入 R4 的重试逻辑。

## 决策定稿(2026-07-15 评审)

- **Q1 依赖:** 暂无依赖 → **v1 假设任务互相独立**,不做依赖解锁。
- **Q3 干完没提交:** **自动重唤醒催他**(短 prompt),救不动再兜底标人。
- **Q2 预算:** 硬顶 **40 分钟**;但**空转超时(默认 12 分钟)才是主闸**(治 429/500/内存卡死,见 R5);
  重唤醒/重试各 **1 次**,仍不行则标人。
